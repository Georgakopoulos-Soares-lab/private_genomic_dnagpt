7. Why Token-SIMD is now the target
-----------------------------------

Current packing constants:
  D                  = 768
  PACK_WIDTH         = 1024
  COPIES             = 4
  configured slots   = 4096
  ring dimension     = 65536

The present implementation places one token in a logical 4096-slot lane:
four identical 1024-slot copies. The same public model matrix is applied to
every token, so repeating the same linear transform once per token discards
the main SIMD opportunity CKKS is intended to provide.

[A] A CKKS ring dimension of 65536 has at most 32768 complex slots. If FIDESlib
    and the OpenFHE context can use a batch size of 32768 while preserving the
    current four-copy BSGS layout, then one ciphertext can hold:

      32768 / 4096 = 8 tokens

    This capacity has not been validated in FIDESlib. The current context is
    explicitly configured for only 4096 slots.

Proposed interleaved physical mapping for B token lanes:

  physical_slot(copy, feature, token) =
      (copy * PACK_WIDTH + feature) * B + token

Properties to prove locally:
  - token is physical_slot modulo B, so rotations by B*k preserve token lanes;
  - each existing logical rotation k becomes physical rotation B*k;
  - public masks/diagonals repeat each logical coefficient for all B tokens;
  - the four-copy wraparound stays within the same token lane;
  - partial final batches do not contaminate active tokens;
  - all client boundaries unpack and repack each token independently.

The attention path needs more than simple linear-layer packing. For a query
batch and key batch, B lane alignments are required to form the B*B score tile.
The intended local design is:
  - interleave B tokens in each Q/K/V ciphertext;
  - rotate/permutate key token lanes through B alignments;
  - compute B encrypted dot products in parallel per alignment;
  - mask causal and partial-batch lanes;
  - send score tiles, not individual score columns, to the client;
  - compute stable full-row softmax at the client;
  - return packed weight tiles;
  - form packed encrypted context tiles against packed V.

[U] Correct wraparound repair for token-lane permutations is the main packing
    question. It must be proved with slot-level NumPy contracts before C++.


8. Transform-count target
-------------------------

Let B be the number of tokens per ciphertext and G=ceil(103/B).

Per block, if all tokenwise dense transforms are Token-SIMD:
  Q/K/V                = 3*G
  attention projection = 1*G
  MLP FC chunks         = 4*G
  MLP projection chunks = 4*G
  total                 = 12*G

For B=8:
  G                     = 13 (12 full batches + final batch of 7)
  products/block        = 156
  products/12 blocks    = 1872
  reduction from today  = 14832 / 1872 = 7.92x

For B=4:
  G                     = 26 (25 full batches + final batch of 3)
  products/block        = 312
  products/12 blocks    = 3744
  reduction from today  = 3.96x

[A] At the existing 14-16 s/product observation, B=8 represents 7.28-8.32
    aggregate GPU-hours of dense transforms. Perfect eight-GPU distribution
    would be 0.91-1.04 h; practical scheduling will be slower.

[A] A sub-three-hour Scheme B result becomes technically plausible only if:
  - B is at least 4-8 with no prohibitive per-product slowdown;
  - attention is tiled so its O(T^2) work/crossings do not dominate;
  - multiple GPUs execute independent packed transforms efficiently;
  - client encrypt/decrypt responses are batched;
  - memory and rotation-key growth remain within the A100 80 GB limit.

[U] This is a research target, not a measured forecast.

    Measured packed output reaches only level 6.

[U] No depth-12 GPU evidence exists.

[U] If depth reduction changes ring_dim from 65536 to 32768, each operation may
    become materially cheaper, but maximum complex slots also fall from 32768
    to 16384. With a 4096-slot logical token lane, Token-SIMD capacity would
    fall from B=8 to B=4. The lower operation cost and lower SIMD width may
    cancel in throughput. Depth and Token-SIMD must therefore be evaluated
    together rather than multiplying two optimistic speedups.
