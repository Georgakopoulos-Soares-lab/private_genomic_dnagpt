\section{Results}
\label{sec:results}

The client-assisted circuit is evaluated along four axes: numerical agreement, executed work,
memory, and complete-inference cost.

\subsection{Evaluation setup and endpoints}

The encrypted input is selected deterministically as the first record in the verified positive
genomic-signal FASTA input. It is one $600$-base-pair fragment, not a random, margin-stratified, or
task-set sample. Local tokenization and embedding produce the $103$-token prompt before encryption;
the measured encrypted endpoint contains all $12$ released blocks and the released task head.

The complete model is executed once on a whole-node allocation with one $40$~GB A100 GPU and $32$
CPU threads; no contention is detected in the recorded telemetry, although scheduler exclusivity
was not requested. Timing starts before weight and reference loading and ends after final
decryption. Server and client roles share one process and node, so boundary calls include
cryptographic work but no serialization or network transport. That single execution supplies
every complete-model timing below; it supports neither a mean nor a service rate. Earlier
contended timings are excluded.

\subsection{Correctness}

Correctness follows the three-link chain in Section~\ref{sec:baseline}. The released float32 path is
recorded separately. The independent NumPy float64 reference is then checked against a float64-cast
PyTorch shadow at $2\times10^{-5}$ for all $12$ blocks and the head, after which encrypted execution
is compared with the NumPy reference. This distinguishes model-dtype drift from CKKS error and
prevents an unchecked reimplementation from judging its encrypted counterpart.

For one block at the $103$-token task prompt, the decrypted output has relative infinity-norm error
$4.64\times10^{-9}$ against an acceptance tolerance of $4\times10^{-2}$ fixed before the run,
leaving seven orders of magnitude of headroom. The worst token-relative error is
$4.7\times10^{-9}$, and the largest absolute deviation is $7.44\times10^{-8}$. These values
establish numerical agreement for the encrypted block with the released weights and exact client
nonlinearities.

The complete model is held to the same unchanged tolerance. Evaluating all $12$ released blocks
and the released task head at the $103$-token task prompt yields a decrypted classification margin
that differs from the manual NumPy float64 margin by $8.56\times10^{-9}$ in relative terms and
$1.05\times10^{-7}$ in absolute terms. The encrypted, manual float64, and released float32 paths all
produce label N for this prompt; relative to the released float32 margin, the encrypted margin
differs by $1.61\times10^{-6}$.

Error accumulates with depth. The
hidden-state relative infinity norm is $4.09\times10^{-9}$ after the first block and
$2.07\times10^{-8}$ after the twelfth, while the largest absolute deviation grows from
$6.56\times10^{-8}$ to $7.97\times10^{-6}$, roughly two orders of magnitude across the model.
Growth of that rate leaves the twelfth-block activation six orders of magnitude inside the
acceptance tolerance. The classification-margin error is $6.67$ orders below the same threshold.
Approximation error accumulates, but it does not change the decision for the evaluated prompt.

The implementation asserts every count in Table~\ref{tab:cost}, the boundary sequence, and the
remaining multiplicative depth before the MLP. Any deviation aborts the run. This turns the
operation schedule into evidence that the optimized implementation executes the same circuit, not
an assurance inferred from a passing output.

Attention dominates the homogeneous boundary-schedule measures: it accounts for $818$ of the
$857$ client calls per block and $818$ of the $896$ ciphertext objects sent across block
boundaries. Boundary optimization is therefore principally an attention problem, even though the
protocol contains three nonlinearity classes. The implementation also checks a heterogeneous
logical-instance counter, but its LayerNorm, GELU, and attention increments have different units
and are not interpreted as scalar work or traffic.

The dense schedule also records the benefit of token packing. Eight-token packing reduces the
serial-equivalent dense-product count from $1{,}236$ to $156$, a $7.92\times$ reduction in
operations. Rotations, masking, client work, and host preparation remain in the packed circuit, so
the factor describes operation count rather than latency.

\subsection{Memory}

Device-wide GPU memory used during the evaluating run reaches $9839$~MiB, within the $40$~GB
device. The GPU was empty at allocation, making attribution to the run reasonable, but the sampler
does not expose a per-process memory metric.

Host memory follows the lifetime of encoded plaintext templates. Query/key/value projection reaches
$25{,}530$~MiB of target-process resident memory. A cache flush precedes attention, whose recorded
resident memory is $12{,}434$~MiB. The MLP holds the largest live weight set and reaches the block
peak of $48{,}610$~MiB. These stage transitions match the explicit flush points in
Section~\ref{sec:optimization}; encoded weights do not accumulate across the entire block.

The two memory results have different mechanisms. The non-interactive composition configuration
exceeded its tested $80$~GB GPU envelope while loading the deep context and evaluation keys.
Client re-encryption shortens the encrypted segments and resets their depth budget, moving that
accelerator-memory barrier. Stage-bounded caching prevents the resulting host-side plaintext
templates from becoming an unbounded second barrier.

The complete model confirms both bounds at full depth. Device-wide GPU memory used rises during
context and key loading, reaches $9839$~MiB after roughly $400$~s, and then holds that value exactly
for the remainder of the run. This matches the single-block footprint, with no growth by block
index. Host resident memory peaks at $50{,}930$~MiB, consistent with the MLP-stage maximum recurring
once per block instead of accumulating. Client assistance therefore removes the accelerator-memory
barrier that stopped the evaluated non-interactive configuration, and the flat device profile across
twelve blocks shows this follows from the depth bound rather than from the particular input.

Two consecutive released blocks compose at reduced sequence length through a full-hidden-state
client refresh, reaching $8.48\times10^{-11}$ relative error after the second block. Device-wide
GPU memory used peaks in the first block and does not increase in the second. This experiment checks the mechanism
used for deeper composition: a fresh encryption starts the next block at level~$0$ without
carrying forward the preceding block's multiplicative depth or GPU-resident temporaries.

The complete model uses that mechanism throughout. All $12$ blocks and the task head
run in one key lineage, separated by $11$ full-hidden-state refreshes between consecutive blocks
and one further refresh of the final token into the head. Multiplicative depth stays at $13$
throughout, the same budget the single block requires, and the run performs no homomorphic
bootstrap at any point. Depth is thus a property of the longest segment between two client
boundaries rather than of network depth, which is what makes the twelve-block key lineage
expressible at all under these parameters.

A complete encrypted inference takes $6683$~s of wall clock, or $1.86$~hours. Encrypted evaluation
accounts for $6594.748$~s of that, and setup is negligible at this scale: context construction and
key generation together take under four seconds, and the single final decryption takes $0.044$~s.
The instrumented phases are a decomposition rather than a partition, leaving $59.504$~s, or $0.9\%$
of wall clock, outside them; Table~\ref{tab:fullcost} shows that remainder rather than distributing
it silently.

Within encrypted evaluation the split between the two parties is exact: the residual provider-side
bucket uses $5638.561$~s and the data owner's boundary work uses $956.187$~s, and the two sum to the
evaluation total without residue. The provider bucket includes GPU-backend work and the host
support around it; it is not GPU-kernel time. The compute provider therefore carries $85.5\%$ of
the encrypted-evaluation interval and the data owner $14.5\%$, with the data owner's share running
on CPU alone. Across $10{,}299$ in-process boundary calls the mean call costs $0.093$~s.

The twelve blocks account for $6565.993$~s and the encrypted task head for $9.046$~s, so the head
is not a meaningful part of the cost. The twelve refreshes together cost $19.710$~s, which places
the price of the composition mechanism at roughly $0.3\%$ of encrypted evaluation. Dividing block
evaluation by twelve gives $547.166$~s per block. The twelve individual block times span
$533.869$~s to $558.943$~s, a spread of $4.7\%$ across architecturally identical blocks on one
node. That bounds within-run scheduling jitter; it is not run-to-run variance, which a single
execution cannot report.

\subsection{Sequence-length structure}

\begin{figure}[tb]\centering
  \includegraphics[width=\textwidth]{fig_scaling.pdf}
  \caption{Causal attention score-tile schedules across the encrypted-scope tasks. Counts follow
  from ciphertext groups rather than from a timing model; only genomic-signal recognition has a
  measured complete inference.}
  \label{fig:scaling}
\end{figure}

Sequence length follows from each task format. Genomic-signal recognition uses $600$ base pairs,
which become $100$ sequence tokens under $6$-mer tokenization; three task-format tokens produce the
$103$-token encrypted anchor. Eight-token packing maps that prompt to $13$ ciphertext groups. The
shorter promoter and splice-site prompts use fewer groups under the same layout, yielding smaller
causal schedules.

The abundance-regression task lies outside the encrypted scope. Its $10{,}500$ base pairs produce
$1{,}755$ tokens and $220$ ciphertext groups under the same tokenization rule. The causal attention
schedule grows quadratically in the number of groups, placing this task in a different circuit-size
regime from the classification prompts.

\subsection{Feasibility}
\label{sec:verdict-feasibility}

Complete-model graph feasibility is established under the stated protocol. All $12$ released
blocks and the task head execute at the task's $103$-token prompt under one key lineage with
declared refreshes. Multiplicative depth remains $13$, device-wide GPU memory used remains
$9839$~MiB after loading, and no homomorphic bootstrap is performed. These are measurements of the
complete computation, not projections from a block.

Numerical generality has a narrower scope. The one selected prompt reproduces the frozen label with
$8.56\times10^{-9}$ relative margin error, but one prompt does not establish encrypted task
accuracy or input-independent stability. The affirmative result is that the executed case meets
the predeclared numerical criterion while composing the complete released graph.

Encrypted token-index lookup and network transport remain outside this verdict, as detailed in
Section~\ref{sec:limitations}.

\subsection{Practicality, judged separately}
\label{sec:verdict-practicality}

Feasibility does not make the current implementation practical. One encrypted classification of
one $600$-base-pair genomic fragment occupies an A100 node for $1.86$~hours and requires an online
key holder throughout, which rules out interactive per-query use in the evaluated form. Suitability
for a specified non-interactive workload has not been measured.

Cross-paper results provide context rather than a controlled verdict. THOR reports $602$~s for a
non-interactive encrypted forward pass of a $12$-layer, $768$-wide encoder at $128$ tokens on a
single A100, at the ring degree, multiplicative depth, and security level used here, with no client
participation at any point~\cite{thor}; the $6683$~s measured here is roughly an order of magnitude
above it at a shorter prompt. Model semantics, nonlinear treatment, packing, software, and
measurement endpoints differ, so this implementation is not performance-leading and the gap does
not isolate the cost of client assistance; Section~\ref{sec:related} sets out the differences.

The measured trace does, however, indicate where that cost sits. Sampled GPU utilization has a
median of $32\%$ and a maximum of $51\%$, so the accelerator is not the saturated resource, even
though the trace does not attribute wall time among encoding, synchronization, memory behavior,
kernel efficiency, and boundary work. Read with the $85.5/14.5$ provider--client split and the
$0.3\%$ cost of the refresh mechanism, this places the optimization target in the provider-side
encrypted path rather than in the interaction the protocol adds. The practicality verdict is
nonetheless negative for the evaluated form: it is too slow for interactive use, and throughput,
serialization, and networked deployment remain unmeasured.
