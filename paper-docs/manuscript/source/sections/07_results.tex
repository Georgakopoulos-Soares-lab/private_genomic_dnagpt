\section{Results}
\label{sec:results}

The client-assisted circuit is evaluated along four axes: numerical agreement, executed work,
memory, and complete-inference cost.

\subsection{Evaluation setup and endpoints}

We evaluate complete encrypted inference at the $103$-token genomic-signal benchmark, the longest
prompt among the encrypted-scope classification tasks. The complete run uses the first verified
positive genomic-signal example, selected deterministically instead of by its prediction margin.
Local tokenization and embedding occur before encryption; the encrypted endpoint contains all $12$
transformer blocks and the task head.

The complete model is executed once on a whole-node allocation with one $40$~GB A100 GPU and $32$
CPU threads; the recorded telemetry shows no evidence of resource contention, although scheduler
exclusivity was not requested. Timing starts before weight and reference loading and ends after final
decryption. Server and client roles share one process and node, so boundary calls include
cryptographic work but no serialization or network transport. That single execution supplies
every complete-model timing below.

\subsection{Correctness}

Before encrypted evaluation, we fixed the relative-error acceptance threshold at
$4\times10^{-2}$. As Section~\ref{sec:baseline} describes, the NumPy float64 reference first agrees
with an independent PyTorch float64 execution after every transformer block and the task head. The
encrypted output is then compared with that checked NumPy reference; the original float32
implementation is recorded separately to distinguish dtype drift from CKKS error.

For one block at the $103$-token benchmark, the decrypted output has relative infinity-norm error
$4.64\times10^{-9}$, leaving seven orders of magnitude of headroom. The worst token-relative error is
$4.7\times10^{-9}$, and the largest absolute deviation is $7.44\times10^{-8}$. These values
establish numerical agreement for the encrypted block with the DNAGPT weights and exact client
nonlinearities.

The complete model is held to the same unchanged tolerance. Evaluating all $12$ transformer blocks
and the task head at the $103$-token benchmark produces the same classification label as the
plaintext reference. The relative classification-margin error is $8.56\times10^{-9}$, or $6.67$
orders of magnitude below the predeclared threshold, and the absolute margin error is
$1.05\times10^{-7}$. The encrypted, NumPy float64, and original float32 paths all produce label N;
relative to the original float32 margin, the encrypted margin differs by $1.61\times10^{-6}$.

CKKS numerical error increases across blocks. The
hidden-state relative infinity norm is $4.09\times10^{-9}$ after the first block and
$2.07\times10^{-8}$ after the twelfth, while the largest absolute deviation grows from
$6.56\times10^{-8}$ to $7.97\times10^{-6}$, roughly two orders of magnitude across the model.
The twelfth-block activation remains six orders of magnitude inside the acceptance tolerance. The
nonlinear functions are evaluated exactly at client boundaries and therefore contribute no
polynomial-approximation error.

\subsection{Memory}

Device-wide GPU memory used during the complete run reaches $9839$~MiB, within the $40$~GB
device. The GPU was empty at allocation, making attribution to the run reasonable, but the sampler
does not expose a per-process memory metric. Host memory follows the stage lifetime of encoded
plaintext templates measured in Section~\ref{sec:optimization}, peaking in the MLP stage of each
block rather than accumulating across the block.

GPU memory reaches $9839$~MiB during initial context and key loading and remains flat across the
twelve transformer blocks. Host resident memory peaks at $50{,}930$~MiB and repeats the same
stage-level pattern in each block instead of accumulating. This behavior is consistent with the
bounded multiplicative depth and stage-scoped plaintext cache used by the client-assisted protocol.

Two consecutive transformer blocks compose at reduced sequence length through a full-hidden-state

and the task head run in one key lineage, separated by $11$ full-hidden-state refreshes between
consecutive blocks and one further refresh of the final token into the head. Fresh client encryption
prevents multiplicative depth from accumulating across transformer blocks: the maximum required
depth remains $13$ throughout the twelve-block execution, and no homomorphic bootstrapping is used.

A complete $103$-token benchmark takes $6683$~s, or $1.86$~hours. Encrypted evaluation accounts for
$6594.748$~s ($98.7\%$) of wall time; setup and final decryption are negligible at this scale.

Within encrypted evaluation, the compute provider accounts for $85.5\%$ and the data owner for
$14.5\%$ (Figure~\ref{fig:systems}(c)); the data-owner share runs on CPU alone. The provider bucket
includes the GPU backend and its host-side preparation, synchronization, and evaluator overhead.

The $1{,}755$-token abundance-regression prompt is outside the encrypted scope and would induce a
substantially larger causal-attention circuit under the current packing.

\subsection{Feasibility}
\label{sec:verdict-feasibility}

Under the stated client-assisted protocol, all $12$ transformer blocks and the task head execute at
the $103$-token benchmark under one key lineage, with a maximum multiplicative depth of $13$,
bounded accelerator memory, and no homomorphic bootstrapping. The resulting prediction satisfies
the predeclared numerical criterion. This establishes complete-model graph feasibility for the
evaluated benchmark; encrypted task accuracy across additional examples remains outside the present
evidence.

\subsection{Practicality, judged separately}
\label{sec:verdict-practicality}

The complete $103$-token benchmark takes $1.86$~hours on one A100 and is therefore unsuitable for
conventional interactive querying in its current form. The intended deployment presents a
different trade-off: a provider retains the model server-side while a data owner accepts additional
latency to prevent a semi-honest provider from observing the genomic input or intermediate
activations in plaintext. For low-volume, privacy-sensitive inference, such a trade-off may still
be useful; this study does not establish production throughput or service-level practicality.
